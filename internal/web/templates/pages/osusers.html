OS users

Operating-system accounts that hold age private keys (for example alice on the linux server, or a no-login daemon like mailsvc).

About OS users, the keystore folder & where sops looks

What an OS user is. A real account on one of your machines - a human login (like alice) or a service/daemon with no login (like mailsvc). SopsHQ places that account's private key (keys.txt) into its keystore folder, owned by and readable only by that account.

The keystore folder. The default is ~/.config/sops/age (the standard sops location), so an account with a home works with no extra setup: sops looks there automatically. You can point it at any other folder instead - for example a folder on an encrypted drive.

Store on a secure drive. Tick the box when adding a user to keep keys.txt on an encrypted drive. SopsHQ writes the real file there and, for an account with a home, makes the default ~/.config/sops/age/keys.txt a symlink to it, so the drive being locked simply makes decryption fail safe rather than leaking the key.

Service accounts with no home. A homeless daemon account (home /nonexistent) cannot use the ~/.config/sops/age default - it needs an explicit, account-owned folder such as /etc/<service>/keys. SopsHQ checks the account with getent (no privileges) and, when a step needs root, shows you the exact sudo commands to run below.

SopsHQ never runs as root. It only does what its own account can do. Creating an account, giving it a home, or making a folder in another account's space are shown as sudo commands for you to run; SopsHQ continues once they are done.

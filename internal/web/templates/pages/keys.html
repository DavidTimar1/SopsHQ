Keys

An age keypair SopsHQ manages. shared = one keypair per project, placed for several users; per_user = one keypair owned by a single user.

About keys & choosing shared vs per-user (security)
What a key is

age (the encryption tool sops uses) works with a keypair: a PUBLIC key (text starting age1..., safe to share - you encrypt TO it) and a PRIVATE key (AGE-SECRET-KEY-1..., the real secret - you decrypt WITH it). SopsHQ generates the pair, stores the private half encrypted in its vault, and places it onto the right machines when you Apply.

Lifecycle
  • Define a key (name + type) here.
  • Generate creates the actual keypair and seals the private half into the vault.
  • Rotate replaces the keypair and re-encrypts the project's secrets to the new one (the old key can then be retired).
Shared vs per-user - the security trade-off

shared: one keypair for the whole project; everyone who may decrypt holds the same private key. Simplest, but to remove one person you must rotate the key and re-encrypt.

per_user: each user has their OWN keypair; the project lists every user's public key, so each person decrypts with their own private key. Removing someone is just dropping their public key and re-keying - no shared secret to rotate. Prefer per-user when more than one person needs access and membership may change.

Set the owner on a per_user key to name the single OS user who owns it. An owned per-user key can then build a global secret set for that owner - its private key lands in the owner's keystore on Apply and the set is encrypted to it. Owner is ignored for a shared key.

The Used column is best-effort: it counts only decrypt events that a machine reported (via the optional sops shim). SopsHQ is not in the decrypt path, so it is not authoritative. See Usage.

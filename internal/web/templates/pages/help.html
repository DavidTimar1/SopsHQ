Terminology and how it works

Plain-language names for everything in SopsHQ, the two-gates rule for reading a secret, and a picture of how the pieces connect.

The two gates

To READ a secret, an OS account needs BOTH of these at the same time:

Gate 1 - the key

A private key that can open the secret, stored in the account's own keystore and readable only by that account. SopsHQ always sets this up.

Gate 2 - the file

Permission to read the encrypted secrets file on disk. In a project folder this is ONE shared file, so other accounts must be able to read that folder (SopsHQ only warns). A secret set gives each account its own private copy, so no shared-folder permission is needed.

Rule of thumb: same folder and same owner -> use a project folder; a separate or service account that should not live in that folder -> use a secret set.

How the pieces connect

OS accounts hold private keys in their keystores. Each private key has a matching public key. A public key is used to encrypt a secret into the secrets file; the matching private key later opens it.

Core objects

Secret
A name plus a value you want kept out of plaintext. Example: STRIPE_KEY = sk_live_....
age key pair
A matched pair made by the age tool: a private key and a public key. (technical: age keypair, X25519 - classical, NOT post-quantum.)
Private key
The secret half (keys.txt); it opens (decrypts) secrets. Guard it like an SSH private key. Stored as an owner-only file.
Public key
The non-secret half (age1...); used when encrypting a secret so the matching private key can later open it. Safe to share.
Secrets file
The file that stores the ENCRYPTED secret values (secrets.yaml). Anyone may read the file; only a private key can open the values inside.
Inner key
One random key sops makes per secrets file that scrambles the values. Each public key you add gets its own encrypted copy of this inner key, stored in a small block at the bottom of the file. Adding a public key is a quick re-encrypt of the inner key, not of every value. (technical: sops data key.)
Helper file
OPTIONAL (.sops.yaml). Tells sops which public keys to use when CREATING or updating a secrets file. Ignored when OPENING one. SopsHQ keeps it.

Accounts and folders

OS account
A real operating-system account, human or service (e.g. alice, or a no-login daemon like mailsvc), that SopsHQ places a private key for. (technical: OS user.)
Keystore folder
The folder that holds one OS account's private key file. Default: ~/.config/sops/age (the sops default location). May be a symlink to a secure drive. (SopsHQ field: KeyBase.) The ~/.config/sops/age default only resolves for an account that HAS a home folder. A homeless service or daemon account (home is /nonexistent or missing) has no ~ to expand, so it needs an EXPLICIT, account-owned keystore path instead (for example /etc/<service>/keys), which SopsHQ creates and makes owner-only; that account's program then points SOPS_AGE_KEY_FILE at the keys.txt inside it.
Key file path
The environment value a program uses to tell sops which private key file to open with (SOPS_AGE_KEY_FILE). If unset, sops uses the default location under that process's home.

Groupings

Project
A NAMED grouping with a folder per machine. SopsHQ writes a secrets file into that folder. It is a SopsHQ record that points at a physical folder; it is not the folder itself. Example: project "Webshop" -> ~/projects/webshop on the server, D:\code\webshop on the laptop.
Secret set
A group of secrets that does NOT belong to any project folder. Stored per account under its keystore at <keystore>/global/<set>/secrets.yaml. A name groups the secrets plus the OS accounts that may open them. A one-account set is "your own global secrets". (technical: GlobalSet.) EACH account you pick gets its OWN owner-only copy in its OWN keystore - there is no shared folder and no cross-account access. That is exactly why a set sidesteps the Gate 2 folder-permission problem: every account reads only its own private copy, so none needs permission to read a folder that belongs to another account.

Actions and rules

Apply
The SopsHQ action that makes keys, places private keys into keystore folders (owner-only), writes or updates the secrets file, and writes the helper file.
The two gates
To READ a secret an account needs BOTH a private key that opens it (in its own keystore, readable only by it) AND permission to read the secrets file on disk. In a project folder there is one shared secrets file (other accounts must be able to read that folder; SopsHQ only warns). A secret set gives each account a private copy (no shared-folder permission needed).
Print-commands
SopsHQ never runs as root. Anything needing privilege (create an OS account, set its home, write into another account's folder) is shown to you as exact sudo commands to run; SopsHQ does the rest unprivileged. (technical: Mode A.)
